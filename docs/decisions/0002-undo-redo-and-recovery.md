# ADR 0002: 操作単位のUndo/Redoとプロセス中断復旧

- 状態: Accepted
- 決定日: 2026-11-13

## 背景

単一イベントIDだけをUndo対象にすると、複数イベントを無効化・生成する出目訂正やスナップショット復元を一つの管理者操作として取り消せない。また、Undo後の新入力で元のブランチを再利用すると、同じターンIDに異なる内容が保存される。

## 決定

- Undo/Redoは `HistoryAction` を単位とする。各操作は有効化したイベントID、無効化したイベントID、変更前後のブランチID、表示ラベルを保持する。
- 開始、出目、一時停止、再開、保存終了、中止、位置訂正、出目訂正、復元を多段Undo/Redoの対象とする。Undo/Redo自体は監査イベントとして残すが対象にしない。
- Undo後に別の操作を行う場合はRedo履歴を破棄し、新しいブランチIDを発行する。これにより取り消したターンと新しいターンのIDを分離する。
- 終了・中止したゲームの訂正、Undo、Redo、復元には `confirmEndedGame: true` を必須とする。未確認時は `ended_game_confirmation_required` を含む409を返す。
- 位置訂正による100への移動は禁止する。ゴール成立の訂正は出目訂正で行う。
- ROLLイベントには `playerId` を保存する。訂正でゴールが早まった場合、既にゴールしたプレイヤーの後続ROLLとゲーム完了後のROLLだけを無効化し、他プレイヤーの実際の出目は順番どおり再適用する。無効化には事前確認を必須とし、監査記録へイベントIDと理由を残す（2026-11-13追記）。
- ゴールを取り消す方向の訂正は、存在しない後続手番を補えないため拒否する。後続ターンをUndoしてから訂正するよう管理者へ案内する。
- 「現在のゲーム」は通常の保存時刻から推測せず、Repositoryの `set_current()` とSQLiteの `app_state` で明示的に保存する。
- 起動時に `IN_PROGRESS` のゲームを検出した場合は、理由 `process_interrupted` の一時停止操作を追記する。中断情報は再開までレスポンスに残す。

## SQLite運用

- 書き込みトランザクションは `BEGIN IMMEDIATE` を使用する。
- journal modeはWAL、`synchronous=NORMAL` とする。単一PC・1 APIワーカーでの応答性とクラッシュ耐性のバランスを優先する。
- 現実装は保存ごとに全イベントと全ターンをupsertし、スナップショットにも操作履歴全体を含める。このため保存容量は履歴長に対して概ねO(n²)で増える。初期規模では単純性を優先し、計測で問題になった時点で差分スナップショットへ移行する。

## 結果

複合操作を含む多段Undo/Redoが再起動後も継続でき、古いゲームの編集だけでプレイヤー画面が切り替わらない。プロセス中断後は管理者が盤面を確認してから明示的に再開できる。

# ADR 0002: 操作単位のUndo/Redoとプロセス中断復旧

- 状態: Accepted
- 決定日: 2026-11-13

## 背景

単一イベントIDだけをUndo対象にすると、複数イベントを無効化・生成する出目訂正やスナップショット復元を一つの管理者操作として取り消せない。また、Undo後の新入力で元のブランチを再利用すると、同じターンIDに異なる内容が保存される。

## 決定

- Undo/Redoは `HistoryAction` を単位とする。各操作は有効化したイベントID、無効化したイベントID、変更前後のブランチID、表示ラベルを保持する。
- 開始、出目、一時停止、再開、保存終了、中止、位置訂正、出目訂正、復元を多段Undo/Redoの対象とする。Undo/Redo自体は監査イベントとして残すが対象にしない。
- Undo後に別の操作を行う場合はRedo履歴を破棄し、新しいブランチIDを発行する。これにより取り消したターンと新しいターンのIDを分離する。
- 終了・中止したゲームの訂正、Undo、Redo、復元には `confirmEndedGame: true` を必須とする。未確認時は `ended_game_confirmation_required` を含む409を返す。
- 位置訂正による100への移動は禁止する。ゴール成立の訂正は出目訂正で行う。
- ROLLイベントには `playerId` を保存する。訂正でゴールが早まった場合、既にゴールしたプレイヤーの後続ROLLとゲーム完了後のROLLだけを無効化し、他プレイヤーの実際の出目は順番どおり再適用する。無効化には事前確認を必須とし、監査記録へイベントIDと理由を残す（2026-11-13追記）。
- ゴールを取り消す方向の訂正は、存在しない後続手番を補えないため拒否する。後続ターンをUndoしてから訂正するよう管理者へ案内する。
- 「現在のゲーム」は通常の保存時刻から推測せず、Repositoryの `set_current()` とSQLiteの `app_state` で明示的に保存する。
- 起動時に `IN_PROGRESS` のゲームを検出した場合は、理由 `process_interrupted` の一時停止操作を追記する。中断情報は再開までレスポンスに残す。

### 中止の扱いの変更（2026-11-18 改訂）

- 中止（`ABORT`）は多段Undo/Redoの対象から外す。中止したゲームでは、訂正・Undo/Redo・復元・
  手番変更・任意ターンからの再開を受け付けず、409 `game_aborted` を返す。上の「終了・中止した
  ゲームの訂正…には `confirmEndedGame: true` を必須とする」のうち、中止についてはこれで置き換える
  （正常終了したゲームは従来どおり確認つきで変更できる）。
- 中止は `reopen`（`REOPEN` イベント、Undo対象外）で取り消し、中止する直前の状態（進行中・
  一時停止中・保存終了・開始前、および手番）へ戻す。直前の状態はイベントの再適用で毎回導くため、
  再開後に中止より前の操作をUndoしても手番が食い違わない。保存済みのゲームを読み込んだ直後でも
  再開できる。
- 管理画面は中止の前に「キャンセル／保存して終了／中止して終了」を選ぶダイアログを出す。
  操作は都度自動保存されるため、「保存して終了」は再開可能な終わり方（`SUSPENDED`）を指す。

### 表示上のターン（2026-11-18 追記）

- 画面に出す「ターン」は、全員が1回ずつ振ると1つ進む数とする（`round`、`roundNumber`）。手番が前の席へ戻った時点で次のターンになる。ゴール済みのプレイヤーは飛ばし、手番変更だけではターンは進まない。
- 出目ごとの通し番号 `turnNumber`／`number` は、楽観ロック（`expectedTurnNumber`）とIDの生成に使うので残す。
- ターンはイベントの再適用で導くため、Undo・出目訂正・復元の後も正しい。導入前に保存したゲームは、読み込み時に再適用して補う。

### 手番変更と任意ターンからの再開（2026-11-18 追記）

- 管理者は進行中・一時停止中のゲームで手番を別のプレイヤーへ変更できる（`TURN_CHANGE`）。
  多段Undo/Redoの対象で、出目訂正の再適用時にも順番どおり適用する。訂正後にその変更が
  不可能または不要になった場合（ゴール済み、すでにそのプレイヤーの手番）は、理由
  `turn_change_not_applicable` で無効化し、事前確認の対象に含める。
- 「ターンNの後から再開」は、現在の有効な履歴をそのターンのROLLの直後で切る操作とする
  （`resume_after_turn`）。版のスナップショットへ戻す「状態復元」と異なり、後から行った
  出目訂正などは残る。ターンの `stateVersionAfter` は訂正で再構築されても作成時の版を
  保つため、版のスナップショットで代用すると訂正前の履歴が戻ってしまうからである。
  監査イベントは `RESTORE`（`targetTurnId`）として残し、Undo/Redoできる。

### 履歴の公開と「ここまで戻す」の記録（2026-11-18 追記）

- ゲームの応答に `timeline`（有効な履歴：出目、位置訂正、手番変更、開始・一時停止・再開など）と `auditLog`（履歴そのものを変えた操作：出目訂正、ここまで戻す・状態復元、Undo/Redo。新しい順）を含める。管理画面はこれを「履歴と訂正」パネルにターンごとに表示する。
- 「ここまで戻す」（`resume-from-turn`）は操作者名と理由を必須とし、`auditLog` に残す。出目訂正の操作者名と理由は、訂正後のターンの `correctedFrom` にも残す。
- 位置訂正の「訂正前の位置」と手番変更の「元の手番」は、再適用のたびに求め直す。前の出目を訂正した後も、表示が実際の履歴と食い違わない。

## SQLite運用

- 書き込みトランザクションは `BEGIN IMMEDIATE` を使用する。
- journal modeはWAL、`synchronous=NORMAL` とする。単一PC・1 APIワーカーでの応答性とクラッシュ耐性のバランスを優先する。
- 現実装は保存ごとに全イベントと全ターンをupsertし、スナップショットにも操作履歴全体を含める。このため保存容量は履歴長に対して概ねO(n²)で増える。初期規模では単純性を優先し、計測で問題になった時点で差分スナップショットへ移行する。

## 結果

複合操作を含む多段Undo/Redoが再起動後も継続でき、古いゲームの編集だけでプレイヤー画面が切り替わらない。プロセス中断後は管理者が盤面を確認してから明示的に再開できる。

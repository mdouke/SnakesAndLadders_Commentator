# ADR 0004: サイコロ認識の状態遷移と確定規則

- Status: Accepted
- Date: 2026-11-13

## Context

実物のサイコロをUSBカメラで読み取り、誤確定や同じサイコロの重複確定を避けながらゲームへ1〜6の出目を渡す必要がある。既存の `dice_recognize/dice_detector.py` は、黒背景上の白いサイコロを単一フレームから検出できるが、動き、時間方向の安定性、確認待ち、重複防止、切断復旧を扱わない。

画像認識の観測とゲーム状態の更新は分離する。認識サービスは候補と根拠を返し、ゲームへのROLL登録はAPI層が `stateVersion` を確認して行う。カメラ画像や映像そのものは通常ログへ記録しない。

## Decision

### 状態遷移

認識セッションは次の状態を持つ。

1. `waiting`: 次の投擲を待つ。ROI内の動きを検出すると `moving`。
2. `moving`: サイコロが動いている。動き量が静止しきい値以下で所定フレーム続くと `stationary`。
3. `stationary`: 単フレーム検出を収集する。同じ値が所定回続いたフレーム内で `candidate` として総合信頼度を計算する。検出なしが除去判定回数続いた場合は、投げられていないか取り除かれたものとして `waiting` に戻る。
4. `candidate`: 時間方向を含む総合信頼度を計算する内部的な遷移状態。次のフレームを待たずに、同じ `observe` 呼び出し内で次へ進む。
   - 自動確定しきい値以上なら `confirmed`。
   - 確認しきい値以上、自動確定未満なら `needs_confirmation`。
   - 確認しきい値未満なら観測を破棄して `stationary` に戻る。
5. `confirmed`: 確定値を呼び出し側へ一度だけ通知する。ゲームへの登録完了通知後に `removal_wait`。
6. `needs_confirmation`: 管理者が候補を承認、1〜6へ修正、または却下する。承認・修正は `confirmed`。却下後は `candidate_rejected` として再移動または手動入力を待ち、同じ静止状態で確認を繰り返さない。
7. `removal_wait`: 同じサイコロを再確定しない。サイコロが所定フレーム見えなくなると `waiting`。十分な再移動を検出した場合は新しい投擲として `moving`。
8. `camera_error`: 切断またはフレーム取得失敗。再接続後は安全のため `waiting` から再開する。

`confirmed` の通知には、プロセス内で生成するセッションUUID v4とセッション内の単調増加連番を組み合わせた `confirmationId` を付ける。同じIDを二度ゲームへ登録してはならない。ゲームへの登録に失敗した場合は `discard_confirmation` で確定を取り消し、元候補を保持した `needs_confirmation` に戻して承認または修正を可能にする。

### 動きと静止

ROIをグレースケール化し、連続フレームの絶対差分の平均を0〜1へ正規化した値を `motionScore` とする。実時間ではなく注入可能な単調増加時計で経過時間を測る。初期値は次のとおりとし、保存画像・映像と実機評価で調整する。

- 動き判定: `motionScore >= 0.08`
- 静止判定: `motionScore <= 0.02` が3フレーム継続
- 候補判定: 同じ出目が3回継続
- 除去判定: 検出なしが3フレーム継続

### 確定用信頼度

総合信頼度は0〜1で、次の加重平均とする。各内訳も観測結果に残し、しきい値調整を可能にする。

| 指標 | 重み | 定義 |
|---|---:|---|
| detector | 0.45 | 輪郭の矩形度、充実度、縦横比から得る単フレーム検出スコアの平均 |
| value stability | 0.30 | 候補窓で最頻値と一致した観測の割合 |
| stillness | 0.15 | `1 - motionScore / stationaryThreshold` を0〜1へ制限した平均 |
| position stability | 0.10 | 検出中心の最大ずれをROI対角長で正規化し、ずれが小さいほど高くする |

初期しきい値は、自動確定 `0.85`、管理者確認 `0.60` とする。総合値だけでなく、出目が1〜6、単一のサイコロだけが検出され、連続条件を満たすことを必須とする。

### 手動操作

- `needs_confirmation` では候補の承認または1〜6への修正を許可する。
- 認識不能時も、管理者は1〜6を手動入力できる。
- 手動値、元候補、信頼度、操作者、理由を区別して監査できる形で後続フェーズのAPIへ渡す。

### カメラとテストの境界

- カメラは列挙・接続・フレーム取得・切断を表すポートで抽象化する。
- OpenCV実装と、保存フレームを返すフェイク実装を用意する。
- 通常テストは保存画像・映像または数値化した観測列を使い、カメラ権限や実機を要求しない。
- 実機評価は別手順とし、認識率、誤確定率、確定までの時間を測る。

### ログ

ADR 0003に従い、UTC、request ID、単調増加時計、1行1 JSONを使う。状態遷移、候補値、信頼度内訳、確定方法、エラーコードは記録してよい。カメラ画像、映像、ROIの画素内容はログへ出さない。

## Consequences

- 単一フレームの誤検出だけではゲームへ出目が登録されない。
- 確定後は除去または明確な再移動までロックされ、重複確定を防げる。
- しきい値は仮値であり、2人のユーザースタディに近い実機データで評価して調整する必要がある。
- Phase 3では認識結果までを実装し、ゲームAPI・WebSocketとの接続はPhase 4で行う。

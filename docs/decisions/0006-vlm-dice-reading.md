# ADR 0006: Claude の画像認識（VLM）によるサイコロの読み取り

- Status: Accepted（2026-11-19 実装。下の「実装時の決定」を参照）
- Date: 2026-11-19

## Context

現在の出目の読み取りは OpenCV の単フレーム検出（ADR 0004）である。2026-11-17 までの改善で誤自動確定は減ったが、
白飛び、ROI の端で切れたサイコロ、盤の奥で側面の目が写る場合など、条件によっては確認依頼が多くなる。
ユーザースタディでは、Claude の画像認識（VLM）で出目を読む方式も試したい。

前提と制約:

- OpenCV 方式はそのまま残し、設定で切り替えられるようにする。VLM が使えない時（キーなし、ネットワーク障害、
  API の失敗）でもゲームを続けられること。
- カメラは約10 FPS。全フレームを API に送ると遅く、費用もかかる。
- API の応答には1〜数秒かかる。待っている間もプレビュー、動きの検出、除去の検出は止めない。
- 画像は外部（Anthropic の API）へ送られる。送る範囲を最小にし、参加者への説明が必要。
- 重複確定の防止、`confirmationId`、確認依頼、手動入力、ゲームとの接続（ADR 0004）の規則は変えない。

## Decision

### 読み取り方式

新しい設定 `readingMode` で次の3つから選ぶ。既定は `opencv`（今の動作）とする。

| `readingMode` | 出目を決めるもの | 自動確定の条件 |
|---|---|---|
| `opencv` | OpenCV の検出（今の方式） | ADR 0004 のとおり |
| `vlm` | Claude の読み取り | サイコロが1個、読み取り可能、確信度 `high` |
| `hybrid` | 両方 | OpenCV の候補と Claude の読み取りが一致し、Claude の確信度が `high` |

`hybrid` で値が食い違った時は確認依頼にし、管理者画面に両方の値を並べて出す。
どの方式でも、自動確定の条件を満たさない時は確認依頼、読み取れない時は手動入力になる。

### いつ API を呼ぶか

動きと静止の判定は今の OpenCV 処理（フレーム差分）をそのまま使う。Claude は「サイコロが投げられて止まった」
と判定された時に、1回の投擲につき1回だけ呼ぶ。

1. `waiting` → `moving` → 静止判定（今の `stationary_frames`）までは今と同じ。
2. 静止したら、その時点のフレームから ROI だけを切り出し、長辺を約768px に縮小して JPEG にする。
3. 新しい状態 `reading`（読み取り中）に入り、API 呼び出しを別スレッドで始める。
   フレーム処理のループは止めない。
4. 応答が来たら、認識ロックを取ってから結果を状態機械へ渡す。
   - 呼び出し中に動き（`movement_threshold` 以上）を検出したら、その投擲の読み取りは取り消す。
     遅れて来た応答は記録だけ残して使わない。新しい投擲として `moving` から始める。
   - サイコロが0個と読まれたら、投げられていないものとして `waiting` に戻る。
   - 2個以上、または読み取れない時は確認依頼（候補なし）にする。
5. 確定した後の `removal_wait`、重複防止、ゲームへの登録は今と同じ。

`vlm` モードでは、OpenCV がサイコロを検出できなくても（白飛びなど）、動いてから止まったら読み取りを行う。
`hybrid` モードでは、OpenCV の候補判定（同値3フレーム）と Claude の応答の両方がそろってから判定する。

古い応答の扱いはコメント生成（ADR 0005）と同じ考え方で、要求ごとに `readingId` を付け、
現在の投擲サイクルの ID と一致する時だけ使う。

### Claude の呼び出し

- 公式の Anthropic SDK（`anthropic` パッケージ、`llm` extra に含まれる）の Messages API を使う。
  画像は base64 の `image` ブロックで送る。
- 出力は構造化出力（`output_config.format` の JSON Schema）で受け取る。

  ```json
  {
    "diceCount": 1,
    "value": 4,
    "readable": true,
    "confidence": "high",
    "note": "上面に4つの目"
  }
  ```

  `value` は1〜6または `null`、`confidence` は `high` / `medium` / `low`。
- プロンプトには「上を向いた面の目の数だけを答える。側面の目は数えない。サイコロが切れている、傾いている、
  重なっている時は `readable=false` または `confidence` を下げる」ことを書く。版は `VLM_PROMPT_VERSION` で管理する。
- モデルは設定で選べるようにする。初期値は評価で決める。候補は速さ重視の `claude-haiku-5-5`、
  中間の `claude-sonnet-5-5`、精度重視の `claude-opus-5-5`。effort は `low` から試す。
- タイムアウトは既定6秒。SDK の自動再試行は切り、タイムアウトと接続エラーだけ1回まで再試行する
  （実況と同じ方針）。
- 失敗した時:
  - `hybrid`: OpenCV だけの結果で判定する（今の `opencv` と同じ動作）。
  - `vlm`: OpenCV の候補があればそれを確認依頼として出し、なければ手動入力にする。
  - どちらも、システムの状態パネルと管理者画面に「画像認識が使えません」と理由を出す。
- API キーは実況と同じ `ANTHROPIC_API_KEY`（`var/secrets.env`）を使う。設定・DB・ログ・画面には出さない。

### 記録

- 新しいテーブル `vision_requests` に、`readingId`、ゲームID・ターン番号、モデル、プロンプトの版、
  所要時間、応答の JSON、エラー、使ったかどうか（`used` / `discarded` / `failed`）を保存する。
  管理者画面で一覧を見られるようにする。
- 認識由来の ROLL には、今の `originalCandidate` と信頼度の内訳に加えて、`recognizer`（`opencv` / `vlm` / `hybrid`）
  と `readingId` を残す。これで後から方式ごとの正解率を比べられる。
- 画像は通常は保存しない。評価用に、設定 `saveImages` をオンにした時だけ、送った画像を Git 管理外の
  `recordings/vlm/` に保存する（既定はオフ）。ログには画像を出さない（ADR 0003・0004）。

### 画面

- 管理者画面の認識パネル: 読み取り方式、モデル、タイムアウト、画像保存の設定、直近の読み取り結果と所要時間、
  「今のフレームを読む」（試し読み、ゲームには登録しない）。
- 確認依頼: `hybrid` で食い違った時は「OpenCV: 3 / Claude: 5」のように両方を出す。
- プレイヤー画面: `reading` 中も今の「認識中」の表示を使う。

### 評価

実装の前に、保存済みの映像で読み取りの精度を確かめる。

- 評価ツール（`services/vision/evaluation.py`）に、静止したフレームを Claude に読ませるモードを追加する。
  同じ画像を何度も送らないよう、応答は画像のハッシュでキャッシュする。
- 2026-11-17 の正解ラベル付き映像（`recordings/dice-evaluation/20261117`）で、OpenCV と比べる。
  比べる値は、正解率、誤った自動確定の数、確認依頼の割合、静止から確定までの時間（中央値・95パーセンタイル）、
  1投擲あたりの費用。
- API の費用がかかるので、実行前に対象の本数と見積もりを出して確認を取る。

## Consequences

- OpenCV の苦手な条件（白飛び、側面の目）で、確認依頼が減る可能性がある。
- 静止から確定までの時間は、API の応答時間（1〜数秒）だけ長くなる。
- 投擲ごとに API の費用がかかる。ネットワークが必要になる。
- ROI の画像（サイコロのトレーと、写り込んだ手など）が外部へ送られる。ユーザースタディの説明と同意書に書く必要がある。
- 状態機械に `reading` が増えるので、ADR 0004 の状態遷移のテストを追加する。
- `opencv` が既定のままなので、VLM を使わない場合の動作は変わらない。

## 実装時の決定（2026-11-19）

上の案から次の点を変えて実装した。

- `hybrid` の流れ: OpenCV が今までどおり候補を判定し、本来なら自動確定または確認依頼になる時点で
  `reading` に入って Claude を呼ぶ（OpenCV が候補を捨てる場合は呼ばない）。判定は次のとおり。
  - 値が一致: Claude の確信度が `high`、または OpenCV の自動確定条件を満たしていれば自動確定。
  - 食い違い: 確認依頼。候補は Claude が `high` ならその値、それ以外は OpenCV の値。画面には両方を出す。
  - Claude が使えない: OpenCV だけの判定（`opencv` モードと同じ結果）。
- `vlm` の流れ: 静止判定のすぐ後に `reading` に入る。OpenCV がサイコロを検出できなくても呼ぶ。
  サイコロ0個なら `waiting` に戻り、読めない・失敗なら `recognition_error`（`vlm_unreadable`、
  `vlm_timeout` など）で手動入力を待つ。
- `vlm` で確定した後は OpenCV の位置が分からないため、次の投擲は明確な動きがあった時だけ始める
  （同じサイコロを二度読まない）。
- 出力は `value` を0〜6の整数（0は読めない）にした。構造化出力が数値の範囲指定に対応しないため。
- 読み取り方式の切り替えは、判定のしきい値と同じく投擲の途中では行わず、次の待機または除去待ちで反映する。
- 記録は `vision_requests` テーブルを作らず、ターンの `recognition`（方式、`readingId`、OpenCV の候補、
  Claude の答え、エラー）と、直近30件の一覧・構造化ログ `vlm_reading` に残す。
  ターンの記録だけで方式ごとの比較ができるため。
- モデルの既定は `claude-sonnet-5-5`。評価の後で見直す。

### トレーの自動検出（2026-11-19 追加）

ROI が四角形だと六角形のトレーの外の机が写り、明るさの判断と Claude に送る画像の両方を乱す。
そこで、ROI の中で一番大きい暗い部分をトレーとして多角形で検出し、その外側を黒く塗った画像を
OpenCV と Claude の両方に使えるようにした（`vision/tray.py`、設定 `trayDetection`、既定オフ）。
トレーが動いても追従するよう、投擲の合間（待機・除去待ちで動きがない時）に探し直し、同じ形が3回
続いた時だけ採用する。形が変わった直後は、明確な動きがあるまで次の投擲を始めない。
